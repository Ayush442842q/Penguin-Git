# ADR 0001 — File watcher excludes build/dependency directories

- **Date:** 2026-08-04
- **Status:** accepted

## Context
`core::watcher::RepoWatcher` used one blanket `RecursiveMode::Recursive` inotify watch over the
entire repo working tree. On a repo with an active build writing continuously into `target/`
(or `node_modules/`, `dist/`, ...), the resulting flood of inotify events pegged a CPU core hard
enough that the whole desktop app appeared to hang — confirmed via live per-thread CPU sampling,
which caught `notify-rs inoti` at ~99% while every other thread, including the GTK main thread,
sat idle. This is not a rare edge case for PenguinGit's actual audience: a git GUI aimed at
developers will very often be pointed at a repo with an active build.

## Decision
Watch directories individually, skipping a fixed exclude-list of build/dependency directory names
(`node_modules`, `target`, `dist`, `build`, `.venv`, `venv`, `__pycache__`, `vendor`, `.next`,
`.nuxt`, `out`, `.cache`, `.turbo`). Pick up newly-created directories as they appear, unless
excluded. Watch `.git` narrowly — top-level files (`HEAD`, `index`, `packed-refs`, ...) plus
`refs/` recursively — instead of folding it into the same blanket recursive watch, which also cuts
event volume from git's own object writes. Filter out `EventKind::Access` events, which carry no
information about a real change and can be generated by watch registration itself.

## Consequences
- Positive: a repo with an active build no longer freezes the app. Also reduces baseline event
  volume from `.git/objects` churn on every commit.
- Negative / cost: watching directories individually instead of one blanket recursive call is more
  code to maintain, and a directory tree that gets deeply restructured in one filesystem operation
  (e.g. `mv` of a large non-excluded subtree from outside the repo) could in principle be watched
  incompletely until the next event triggers a re-walk — not observed in testing, but worth knowing.
- **Invariant added to context-graph.json:** `watcher-excludes-build-output`

## Alternatives rejected
- **Debounce harder / rate-limit the callback** — doesn't help; the CPU cost is in inotify reading
  and dispatching the flood of raw events before any debounce logic runs, not in how often the
  callback fires.
- **Respect `.gitignore` via the `ignore` crate** — more correct in the general case, but adds a
  new dependency and doesn't fix the acute pain point any faster than a fixed exclude-list; revisit
  if the fixed list proves insufficient in practice.
